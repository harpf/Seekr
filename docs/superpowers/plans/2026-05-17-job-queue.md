# Persistent Job Queue Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Replace the three in-memory job dictionaries (`jobs`, `ai_jobs`, `_update_job` — partial) in `app.py` with a single persistent `jobs` SQLite table, a `JobStore` service, and a polling `Worker` that runs in a background thread, supports concurrent execution (bounded), retry-with-backoff, and restart-recovery.

**Architecture:** One `jobs` table holds every job's state. A `JobStore` service is the only place that touches the table. A `Worker` instance is created once at app startup, runs a poll loop in its own thread, claims pending jobs atomically (`UPDATE ... RETURNING`), and dispatches each to a registered handler in a sub-thread (bounded by a semaphore). Handlers receive a `progress_cb` they can call to publish progress. Handlers raise on error; the worker translates raises into retry-or-fail. At startup, any `running` jobs are marked `interrupted` — the operator decides whether to re-enqueue.

**Tech Stack:** Python 3.11, SQLite (`UPDATE ... RETURNING` is available; sqlite 3.40+ ships with Python 3.11), threading, pytest. No new third-party deps.

**Scope boundaries:**

In scope:
- `jobs` table schema + idempotent `_mark_interrupted_running_jobs` at startup.
- `JobStore` service module.
- `Worker` class with handler registry and poll loop.
- Migration of three job categories:
  - **index_paths** (used by `/api/index/start` and `/api/ha/index`)
  - **ai_suggest_structure** (used by `/api/ai/suggest-structure`)
  - **ai_reorganize** (used by `/api/ai/reorganize/start`)
- Backward-compatible `GET /api/index/jobs/{job_id}` and `GET /api/ai/jobs/{job_id}` — response shapes preserved.
- ACL: every job records `owner_user_id`. The GET endpoints check that the caller is the owner OR an admin.
- Tests: queue mechanics with synthetic handler, restart recovery, retry, plus light structural tests for the real migrations.

Out of scope (deferred to later plans):
- `/api/ai/pull-model` jobs (Ollama-driven, distinct lifecycle — leave as-is).
- `_update_job` (system-update job that replaces the running process — persisting it makes no sense).
- Job cancellation API.
- Multi-process / distributed workers.
- Job priorities, deadlines, or lane affinity.
- A UI list view of all jobs (only `GET /api/{index|ai}/jobs/{id}` is touched here).

## Key design decisions (locked)

- **Job IDs are integers** in the DB; APIs expose them as `str(id)`. Existing clients treat `job_id` as opaque (hex uuid today), so a decimal string is wire-compatible.
- **States:** `pending` | `running` | `succeeded` | `failed` | `interrupted`. No `cancelled` (out of scope).
- **Concurrency:** the worker spawns one sub-thread per claimed job, bounded by a semaphore (default 4). Existing in-memory behaviour spawned unbounded daemon threads; this caps the resource usage while preserving multi-job concurrency.
- **Retry:** if a handler raises, JobStore increments `retry_count`. If `retry_count < max_retries`, the job is re-scheduled with `next_attempt_at = now + min(2**attempt, 600)` seconds (capped at 10 min). Otherwise it becomes `failed`. Default `max_retries=0` (today's behaviour — fail immediately on error).
- **Restart recovery:** at startup, every `running` job is bulk-updated to `interrupted`. No auto-resume — the operator looks at the dashboard and re-enqueues if appropriate. (Resume semantics differ per kind, and would belong in a later plan.)
- **Handler signature:**
  ```python
  def handler(payload: dict, progress_cb: Callable[[dict], None]) -> dict
  ```
  Returns the final result dict (stored in `result_json`). Raises any exception to signal failure (worker captures `str(exc)` into `error_message`).
- **Workers don't see ACLs.** Jobs are scoped by `owner_user_id` at the API surface, not in the worker's claim. This keeps the worker simple; ACL leak would require the GET endpoints to compare `owner_user_id` against the current user.

```python
"""Persistent job queue. The only module that writes to the `jobs` table.

Concurrency model: each method is one short SQL statement (or two within a
single connection transaction). The shared SqliteStore connection uses WAL
mode with a 5 s busy_timeout, so concurrent calls serialise cleanly.
"""
from __future__ import annotations

import json
from datetime import UTC, datetime, timedelta
from typing import Any

from document_search.index.sqlite_store import SqliteStore


_VALID_STATES = ("pending", "running", "succeeded", "failed", "interrupted")


class JobStore:
    def __init__(self, store: SqliteStore):
        self.store = store
        self.conn = store.conn

    @staticmethod
    def _now() -> str:
        return datetime.now(tz=UTC).isoformat()

    def enqueue(
        self,
        kind: str,
        payload: dict,
        owner_user_id: int | None = None,
        max_retries: int = 0,
    ) -> int:
        now = self._now()
        cur = self.conn.execute(
            "INSERT INTO jobs(kind, state, payload_json, retry_count, max_retries, "
            "owner_user_id, created_at) VALUES(?, 'pending', ?, 0, ?, ?, ?)",
            (kind, json.dumps(payload), max_retries, owner_user_id, now),
        )
        self.conn.commit()
        return int(cur.lastrowid)

    def get(self, job_id: int) -> dict | None:
        row = self.conn.execute(
            "SELECT * FROM jobs WHERE id=?", (job_id,)
        ).fetchone()
        return dict(row) if row else None

    def claim_next(self, kinds: list[str] | None = None) -> dict | None:
        """Atomically pick the next runnable pending job and mark it running.

        UPDATE ... RETURNING is atomic in SQLite 3.35+; we ship on Python 3.11
        which bundles SQLite >= 3.40.
        """
        now = self._now()
        if kinds:
            placeholders = ",".join("?" * len(kinds))
            sql = f"""
                UPDATE jobs SET state='running', started_at=?
                WHERE id = (
                  SELECT id FROM jobs
                  WHERE state='pending'
                    AND (next_attempt_at IS NULL OR next_attempt_at <= ?)
                    AND kind IN ({placeholders})
                  ORDER BY id LIMIT 1
                )
                RETURNING *
            """
            params: tuple = (now, now, *kinds)
        else:
            sql = """
                UPDATE jobs SET state='running', started_at=?
                WHERE id = (
                  SELECT id FROM jobs
                  WHERE state='pending'
                    AND (next_attempt_at IS NULL OR next_attempt_at <= ?)
                  ORDER BY id LIMIT 1
                )
                RETURNING *
            """
            params = (now, now)
        row = self.conn.execute(sql, params).fetchone()
        self.conn.commit()
        return dict(row) if row else None

    def update_progress(self, job_id: int, progress: dict) -> None:
        self.conn.execute(
            "UPDATE jobs SET progress_json=? WHERE id=?",
            (json.dumps(progress), job_id),
        )
        self.conn.commit()

    def mark_succeeded(self, job_id: int, result: dict | None) -> None:
        self.conn.execute(
            "UPDATE jobs SET state='succeeded', result_json=?, finished_at=? WHERE id=?",
            (json.dumps(result) if result is not None else None, self._now(), job_id),
        )
        self.conn.commit()

    def mark_failed(self, job_id: int, error_message: str) -> None:
        """Failure path. If retries are available, re-schedule with backoff;
        otherwise transition to 'failed'."""
        row = self.conn.execute(
            "SELECT retry_count, max_retries FROM jobs WHERE id=?", (job_id,)
        ).fetchone()
        if row is None:
            return
        attempt = row["retry_count"] + 1
        if attempt > row["max_retries"]:
            self.conn.execute(
                "UPDATE jobs SET state='failed', error_message=?, "
                "retry_count=?, finished_at=? WHERE id=?",
                (error_message, attempt, self._now(), job_id),
            )
        else:
            backoff_s = min(2 ** attempt, 600)
            next_at = (datetime.now(tz=UTC) + timedelta(seconds=backoff_s)).isoformat()
            self.conn.execute(
                "UPDATE jobs SET state='pending', error_message=?, "
                "retry_count=?, next_attempt_at=?, started_at=NULL WHERE id=?",
                (error_message, attempt, next_at, job_id),
            )
        self.conn.commit()

    def mark_interrupted_running_jobs(self) -> int:
        """Called at app startup. Any job left in 'running' state is from a prior
        process that exited without finishing it; mark interrupted so operators
        can decide what to do."""
        cur = self.conn.execute(
            "UPDATE jobs SET state='interrupted', finished_at=? WHERE state='running'",
            (self._now(),),
        )
        self.conn.commit()
        return cur.rowcount

    def list_jobs(
        self,
        owner_user_id: int | None = None,
        state: str | None = None,
        kind: str | None = None,
        limit: int = 100,
    ) -> list[dict]:
        clauses = []
        params: list[Any] = []
        if owner_user_id is not None:
            clauses.append("owner_user_id=?")
            params.append(owner_user_id)
        if state:
            clauses.append("state=?")
            params.append(state)
        if kind:
            clauses.append("kind=?")
            params.append(kind)
        where = ("WHERE " + " AND ".join(clauses)) if clauses else ""
        sql = f"SELECT * FROM jobs {where} ORDER BY id DESC LIMIT ?"
        params.append(limit)
        return [dict(r) for r in self.conn.execute(sql, tuple(params)).fetchall()]
```

```python
"""Background worker for the persistent job queue.

Lifecycle:
  worker = Worker(job_store, max_concurrent=4)
  worker.handler("kind")(callable)        # register handlers
  worker.start()                          # spawn poll thread
  ...
  worker.stop()                           # stop poll thread, wait for in-flight

For tests, use `worker.tick()` to manually advance one poll cycle without
running the background thread.
"""
from __future__ import annotations

import logging
import threading
import time
from typing import Callable

from document_search.services.job_store import JobStore

log = logging.getLogger(__name__)

Handler = Callable[[dict, Callable[[dict], None]], dict | None]


class Worker:
    def __init__(
        self,
        job_store: JobStore,
        max_concurrent: int = 4,
        poll_interval_s: float = 1.0,
    ):
        self.job_store = job_store
        self.max_concurrent = max_concurrent
        self.poll_interval_s = poll_interval_s
        self._handlers: dict[str, Handler] = {}
        self._semaphore = threading.BoundedSemaphore(max_concurrent)
        self._inflight: set[threading.Thread] = set()
        self._inflight_lock = threading.Lock()
        self._stop_event = threading.Event()
        self._poll_thread: threading.Thread | None = None

    def handler(self, kind: str):
        """Decorator: register a handler for a job kind."""
        def decorator(fn: Handler) -> Handler:
            self._handlers[kind] = fn
            return fn
        return decorator

    def register(self, kind: str, fn: Handler) -> None:
        self._handlers[kind] = fn

    def start(self) -> None:
        if self._poll_thread is not None:
            return
        self._stop_event.clear()
        self._poll_thread = threading.Thread(target=self._poll_loop, name="JobWorker", daemon=True)
        self._poll_thread.start()

    def stop(self, timeout: float = 5.0) -> None:
        self._stop_event.set()
        if self._poll_thread is not None:
            self._poll_thread.join(timeout=timeout)
            self._poll_thread = None
        self.wait_until_idle(timeout=timeout)

    def wait_until_idle(self, timeout: float = 5.0) -> None:
        """Block until all in-flight handlers have finished or timeout."""
        deadline = time.monotonic() + timeout
        while True:
            with self._inflight_lock:
                threads = [t for t in self._inflight if t.is_alive()]
            if not threads:
                return
            if time.monotonic() >= deadline:
                return
            for t in threads:
                t.join(timeout=min(0.1, max(0.0, deadline - time.monotonic())))

    def tick(self) -> int:
        """Process one poll cycle: claim as many jobs as `max_concurrent` allows
        and dispatch each in its own thread. Returns the number dispatched.

        Intended for tests; production code calls `start()` which runs `tick`
        in a loop.
        """
        dispatched = 0
        while True:
            if not self._semaphore.acquire(blocking=False):
                return dispatched
            job = self.job_store.claim_next()
            if job is None:
                self._semaphore.release()
                return dispatched
            t = threading.Thread(target=self._execute, args=(job,), name=f"Job-{job['id']}")
            with self._inflight_lock:
                self._inflight.add(t)
            t.start()
            dispatched += 1

    def _poll_loop(self) -> None:
        while not self._stop_event.is_set():
            try:
                self.tick()
            except Exception:
                log.exception("Worker poll loop error")
            self._stop_event.wait(self.poll_interval_s)

    def _execute(self, job: dict) -> None:
        try:
            job_id = job["id"]
            kind = job["kind"]
            handler = self._handlers.get(kind)
            if handler is None:
                self.job_store.mark_failed(job_id, f"no handler registered for kind '{kind}'")
                return
            import json
            payload = json.loads(job["payload_json"])

            def progress_cb(p: dict) -> None:
                self.job_store.update_progress(job_id, p)

            try:
                result = handler(payload, progress_cb)
            except Exception as exc:
                log.exception("Handler %s failed for job %s", kind, job_id)
                self.job_store.mark_failed(job_id, f"{type(exc).__name__}: {exc}")
                return
            self.job_store.mark_succeeded(job_id, result if isinstance(result, dict) else None)
        finally:
            with self._inflight_lock:
                self._inflight.discard(threading.current_thread())
            self._semaphore.release()
```

def test_retry_recovers_from_transient_failure(tmp_path):
    """A handler that fails the first time then succeeds: end state is succeeded,
    retry_count == 1."""
    from document_search.app import create_app
    from document_search.services.job_store import JobStore

    db = tmp_path / "t.db"
    app = create_app(str(db))
    attempts = []

    @app.state.worker.handler("flaky_demo")
    def _flaky(payload, progress_cb):
        attempts.append(1)
        if len(attempts) == 1:
            raise RuntimeError("transient")
        return {"ok": True}

    with TestClient(app):
        job_id = app.state.job_store.enqueue("flaky_demo", {}, max_retries=2)
        # The worker is running; wait for retry cycle.
        # Backoff is 2**1 = 2s; force next_attempt to now so we don't wait.
        import time
        deadline = time.monotonic() + 6
        while time.monotonic() < deadline:
            job = app.state.job_store.get(job_id)
            if job["state"] == "pending" and job["retry_count"] >= 1:
                # Speed up retry
                app.state.job_store.conn.execute(
                    "UPDATE jobs SET next_attempt_at=NULL WHERE id=?", (job_id,)
                )
                app.state.job_store.conn.commit()
            if job["state"] in ("succeeded", "failed"):
                break
            time.sleep(0.05)
        assert job["state"] == "succeeded"
        assert job["retry_count"] == 1

## Notes for the executing agent

- **Why a separate `_startup_db = SqliteStore(...)` for the worker:** the existing `store()` helper returns a per-request-thread store via `_thread_local`. The worker thread isn't a request thread, so it would create yet another store on first use. By instantiating one explicitly at app startup, we make the worker's DB usage observable and easy to swap out in tests. The worker uses this store's connection for `JobStore` operations; per-job handlers create their own `SqliteStore(Path(db_path))` for document operations (this is exactly how the existing route's `runner` did it).
- **Why `UPDATE ... RETURNING` for claim:** it's atomic in SQLite 3.35+. Python 3.11 ships with SQLite 3.40+. A `SELECT then UPDATE` pair would race between two workers — but we currently run only one worker. The atomic form costs nothing extra and future-proofs for multi-worker.
- **Why retry uses exponential backoff with a 600 s cap:** index/AI failures are typically either (a) transient (filesystem hiccup, Ollama briefly unavailable — retry minutes later helps) or (b) deterministic (corrupted file, wrong path — retry doesn't help). Backoff lets transient failures heal without spinning, and the 600 s cap prevents a stuck job from monopolising retry slots forever.
- **Why no auto-resume of interrupted jobs:** resuming a partially-completed indexing run requires checkpoint state that doesn't exist in the current schema. Adding it is a future plan. The current behaviour ("operator decides") is safer.
- **Why the un-migrated `_update_job` and `ai_pull_model` stay:** the system-update job replaces the running Python process (the new process should NOT auto-resume the old job — it's already done). The pull-model job is driven by Ollama and has its own retry/progress semantics; migrating it requires a dedicated handler that streams from `/api/pull` — a separate task.
- **What `progress_cb` does NOT do:** it doesn't notify subscribers, doesn't trigger UI refreshes. The frontend still polls. Adding push notifications (WebSocket / SSE) is a future plan.
- **CAUTION when migrating `_handle_ai_reorganize`:** the existing route body interleaves AI calls with progress writes. Copy carefully and don't reorder calls — the existing user-visible progress arrives incrementally, and that experience must be preserved.
